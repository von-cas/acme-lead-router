# acme-lead-router

A demo service for a GoHighLevel + n8n speed-to-lead build for a made-up company, Acme Solar.
n8n calls it to score a lead with an AI model and to map the lead to a buyer's format. It also
stands in for the buyer's CRM, with a switch that simulates an outage.

| Endpoint | Auth | What it does |
| --- | --- | --- |
| `GET /health` | none | Liveness check |
| `POST /qualify` | `X-Service-Token` | Cleans the lead, scores it with the AI model, falls back to rules if the model fails |
| `POST /map/{buyer_id}` | `X-Service-Token` | Maps a lead to that buyer's format; 422 if a required field is missing |
| `POST /mock-buyer/{buyer_id}/leads` | `Authorization: Bearer <buyer key>` | Fake installer CRM; `?outage=1` answers 503, `?reject=1` answers 422 |

How the scoring call is built:

- `LLM_PROVIDER` picks the model: `deepseek` (default, `deepseek-flash` in JSON mode) or `claude`
  (`claude-opus-5-5` at low effort with a JSON schema and server-side fallbacks).
- Only the scoring facts go to the model: no name, email or phone.
- The model's JSON is validated with pydantic. Tier thresholds (hot from 75, warm from 45) live in code.
- Any failure (no key, timeout, bad JSON, a score out of range) falls back to a rules score marked
  `source: rules`, so the lead keeps moving.

## Run it

```bash
uv venv --python 3.12 .venv
uv pip install --python .venv/bin/python -r requirements-dev.txt
.venv/bin/python -m pytest -q
```

Environment variables: `DEEPSEEK_API_KEY` (or `LLM_PROVIDER=claude` with `ANTHROPIC_API_KEY`),
`SERVICE_TOKEN`, `BUYER_KEY` (see `.env.example`).
Deploys to Vercel as a FastAPI app with zero config (`vercel deploy --prod`).

## Example

```bash
curl -s -X POST https://<your-app>.vercel.app/qualify \
  -H "X-Service-Token: $SERVICE_TOKEN" -H "Content-Type: application/json" \
  -d '{"contact_id":"t1","first_name":"Maria","email":"maria@example.com","phone":"5125550101","postal_code":"78704","monthly_bill":220,"homeowner":"Yes","roof_shade":"None","timeline":"ASAP","consent":"yes"}'
```

## n8n workflows

`n8n/` holds two importable workflows, generated by `tools/build_n8n.py`:

- `STL-01-qualify-and-deliver.json`: three triggers in one workflow.
  - Webhook from GoHighLevel: checks a key, answers 202, scores the lead through `/qualify`, writes the score,
    tier tag and a note back to GoHighLevel, then for consented hot or warm homeowners checks the delivery ledger
    for duplicates and the daily cap, maps the lead and posts it to the buyer with 3 retries.
  - Every 15 minutes: replays failed deliveries, up to 5 attempts, then tags `delivery-dead` and alerts.
  - Every day at 8 AM Central: posts yesterday's counts to Slack, and warns when there were no deliveries.
- `STL-99-error-alert.json`: posts any n8n crash to Slack. Set it as STL-01's error workflow.

The delivery ledger lives in the workflow's static data, so the three triggers share it without a database.
n8n saves static data only for production runs of an active workflow, not for manual test runs.

After importing, select a Header Auth credential on each HTTP node that has one empty
(GHL PIT, Lead Router, Installer A), and create these variables:
`ROUTER_URL`, `WEBHOOK_KEY`, `GHL_FIELD_AI_SCORE`, `GHL_FIELD_AI_TIER`, `GHL_FIELD_AI_SUMMARY`,
`INSTALLER_A_DAILY_CAP`, `INSTALLER_A_URL` (the buyer's lead endpoint; in the demo the mock buyer, with
`?outage=1` added to simulate an outage), `SLACK_ALERT_URL`.

Known limit: static data is written when a run ends, so two runs at the same moment can both pass the
duplicate check. A production build keeps the ledger in a database row claimed atomically; until then
the buyer's `Idempotency-Key` (one per submission) is the backstop.
